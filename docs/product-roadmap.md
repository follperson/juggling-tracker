# Product roadmap

The first user is a solo juggler with a phone recording who wants to know “How long was my best run, and did that ending count as a drop?” Make the answer inspectable even when the tracker misses a ball. The first release target is a local recorded-video review for the three-ball cascade. The path to a general counter adds new conditions and patterns behind the same session, replay and correction workflow. [Research plan and evidence](research-plan.md)

| Milestone | What the juggler can do | What unlocks the next milestone |
|---|---|---|
| Measure an ordinary practice recording — in progress | Reviewers can score saved ball detections at source-frame timestamps, separate airborne from held balls, and link an error to the original recording. Existing CLI commands already analyze whole sessions and render video overlays. | Complete a development pilot with counts, run boundaries, genuine drops, deliberate endings and negative controls. Replay a dense manual trajectory through the analyzer to identify the limiting stage. The [initial size comparison](research-plan.md#first-controlled-experiment) rules out an obvious default change on the measured failure. |
| Review a recorded practice session | Open one local video. See the detected runs, catches per run, best streak and proposed drops. Select a run or a disputed ending to seek the original video. Show “could not establish a run” when coverage is inadequate. Save an edited count or ending and reopen the session with both the original prediction and correction intact. | A tester can correct an undercount and dismiss a false drop without instructions or JSON editing. On re-analysis the original prediction, analysis version, source identity and manual corrections remain distinguishable. Pass the offline beta criteria below before advertising automatic counting accuracy. |
| Use a counter during practice | Start a camera session, distinguish a provisional count from a confirmed catch, recover from a miss, and review the saved session afterward. | On a named device complete uninterrupted live sessions, including pauses and pickups. Meet the recorded-video gates on labeled replays, the throughput floor below, and publish event lag and long-session duplicate counts. Confirm camera-session behavior on the device. [Live duplicate work](https://github.com/follperson/juggling-tracker/pull/53) |
| Support more juggling | Run the same capture and review flow for a four-ball fountain and mixed-height throws, then extend to more ball counts and patterns. Report each pattern and camera condition that qualifies. | Repeat the held-out cohort and end-to-end tests for every advertised family. Add explicit scoring rules before including multiplex catches, bouncing, clubs, rings or multiple jugglers. A supported family needs both a recording-level verdict and a correction flow users understand. |

### Proposed offline beta criteria

Carry forward the original targets of catch count within one on at least 90% of labeled runs and temporal intersection-over-union of at least 0.90 on 80% of labeled runs. Provisional drop precision and recall are each at least 0.80. Preserve all raw overcount and reference regression gates on the extraction branch. [Original design targets](superpowers/specs/2026-07-15-juggling-tracker-rebuild-design.md)

As a proposed minimum for an initial beta decision, collect at least 30 labeled runs, 20 genuine misses and 20 minutes of non-juggling controls across at least six held-out performers, with both close and wide framing. Report false catches per control minute, spurious runs, each missed run and the worst represented condition. A false run in a control requires review before promotion. Count multiple runs from one person together when describing uncertainty. These are pilot release criteria. A claim about another population requires evaluation there.

For live use, retain the design's 15 fps floor and 30 fps goal on the named target device. Include decode, detection, counting and display. Record the delay from visible reception to confirmed count, and measure consecutive false confirmations during a deliberate stop. Agree on an acceptable delay with jugglers in the recorded-review pilot before freezing the live acceptance test. [Live design](superpowers/specs/2026-07-15-juggling-tracker-rebuild-design.md)

### Implementation order and decision ownership

1. **Evaluation and data.** Maintain a recording register, two separate annotation tracks for raw observations and corrections to model output, and one command per reproducible comparison. The required assets and next experiment are in the [research plan](research-plan.md).
2. **Offline application.** Put the supported package behind a thin local review interface. Reuse `SessionResult`, `VideoLabels`, rendered overlays and the saved-detection replay path. Store corrections separately with the source digest and timestamp. Verify import, seek, edit, reopen and export on real recordings. The older interface in `legacy/` is a source of workflow examples.
3. **Live and distribution.** Build the live view on the same session and correction contracts. Profile a real target device before selecting its runtime or porting the model. Before distributing weights or footage, the owner records permissions for that use and chooses the code and model distribution terms.

The project maintainer records the evidence and reason for each promotion. Participants determine whether a disputed motion was intended as a catch, collection or miss when video alone cannot resolve it. Publish aggregate results, test procedures and supported conditions. Keep private recordings, identifying metadata and unpublished weights in the owner's evidence store.
